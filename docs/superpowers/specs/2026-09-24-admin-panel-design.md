# Русская админ-панель Flytopay — дизайн первой версии

## Цель

Создать полноценную русскоязычную web-админку Flytopay с реальной статистикой,
поиском пользователей, просмотром их данных и безопасным управлением статусом
пользователя и его сессиями.

## Границы первой версии

В первую версию входят:

- русскоязычный responsive layout админки;
- shadcn-style UI-компоненты на существующих React/Radix-зависимостях;
- dashboard с реальными агрегатами из PostgreSQL;
- динамика регистраций, платежей и выпусков по дням;
- состояние backend, базы данных, Redis/Celery и CaaS на основе доступных
  backend-проверок;
- список пользователей с поиском по UUID, Telegram ID и username;
- фильтры по статусу и периоду активности;
- сортировка и серверная пагинация;
- карточка пользователя с аккаунтами Telegram, статусом, картами, платежами,
  арендами и балансом;
- блокировка и разблокировка пользователя;
- отзыв активных сессий пользователя;
- запись всех изменяющих действий в существующий `admin_audit_events`;
- русские названия разделов, статусов, ошибок, пустых состояний и действий.

Во вторую версию откладываются ручные финансовые корректировки, возвраты,
массовые финансовые операции, управление тарифами, рассылки и изменение
production-конфигурации.

## Backend API

Существующие `/api/v1/admin/overview` и коллекционные endpoints сохраняются
для совместимости, но UI первой версии использует новые контракты:

```text
GET  /api/v1/admin/dashboard
GET  /api/v1/admin/users?q=&status=&activity=&page=&limit=&sort=&order=
GET  /api/v1/admin/users/{user_id}
POST /api/v1/admin/users/{user_id}/block
POST /api/v1/admin/users/{user_id}/unblock
POST /api/v1/admin/users/{user_id}/revoke-sessions
GET  /api/v1/admin/activity?page=&limit=
GET  /api/v1/admin/system
```

Каждый endpoint, кроме публичной проверки `/status`, использует существующий
admin permission dependency. Просмотр требует `admin.read`, изменение статуса
пользователя — `admin.users.write`, отзыв сессий — `admin.sessions.write`.

Изменяющие endpoints требуют CSRF, UUID пользователя и JSON-тело с обязательной
причиной действия. Ответы не содержат PAN, CVV, session token, webhook secret
или другую чувствительную информацию. Повторное выполнение одного запроса не
создаёт второе действие в audit log при одинаковом Idempotency-Key.

## Реальная статистика

Dashboard считает и возвращает:

- общее количество пользователей и Telegram-аккаунтов;
- активных, заблокированных и новых пользователей за сегодня, 7 и 30 дней;
- количество карт, demo-карт и активных аренд;
- количество платежей по статусам и сумму успешных платежей;
- количество кошельков и доступный общий баланс;
- массив дневных точек за последние 30 дней для пользователей, платежей и
  выпусков;
- последние admin-аудит события.

Агрегации строятся SQL-запросами с UTC-границами периода. Если интеграция
недоступна, dashboard показывает её статус как `unknown` с описанием ошибки,
но не подменяет реальные бизнес-метрики демонстрационными значениями.

## Пользователи и действия

Список возвращает только поля, необходимые для таблицы: UUID, Telegram ID,
username, отображаемое имя, статус, дату регистрации, последнюю активность,
количество карт, активность аренды и агрегированный баланс. Полные детали
загружаются отдельным запросом.

Блокировка устанавливает `User.status = "blocked"`, инвалидирует активные
сессии и пишет событие `user.block`. Разблокировка устанавливает `active` и
пишет `user.unblock`. Отзыв сессий не изменяет статус и пишет
`user.revoke_sessions`. Нельзя заблокировать текущего bootstrap-владельца
админки через этот интерфейс.

## Frontend

Админка будет разделена на компоненты по ответственности:

- `components/admin/ui/*` — Button, Card, Badge, Input, Select, Dialog, Table,
  Pagination, Skeleton и Toast;
- `components/admin/AdminLayout.tsx` — боковая навигация и responsive shell;
- `components/admin/AdminDashboard.tsx` — метрики, графики и system status;
- `components/admin/AdminUsers.tsx` — фильтры, таблица и пагинация;
- `components/admin/AdminUserDetails.tsx` — профиль и подтверждение действий;
- `components/admin/AdminActivity.tsx` — журнал audit событий.

Страница `/admin` сохраняет текущую точку входа и проверку admin-доступа.
Таблицы используют компактный desktop layout и горизонтальную прокрутку на
узких экранах. Опасные действия выполняются только после явного подтверждения
в Dialog.

## Проверки

Backend:

- unit tests для агрегатов, фильтров и permission checks;
- route tests для поиска, пагинации, block/unblock и revoke sessions;
- проверка audit событий и запрета bootstrap-владельца;
- `ruff check src tests`;
- `python -m pytest -q`.

Frontend:

- typecheck компонентов и API-типы;
- форматирование;
- production build;
- ручная проверка русских подписей и responsive layout по существующим
  breakpoint-правилам.

## Решения по безопасности

- API key CaaS остаётся только на backend;
- в админском UI не отображаются PAN и CVV;
- все операции над пользователями защищены существующим admin allowlist/RBAC;
- audit log не содержит токены и секреты;
- массовые и финансовые операции не входят в первую версию.

## Самопроверка спецификации

- Все согласованные пользователем направления первой версии покрыты разделами
  API, статистики, пользователей, frontend и проверок.
- Границы явно исключают финансовые корректировки и другие опасные операции,
  для которых пока нет отдельного workflow подтверждения.
- API использует существующую RBAC/audit-инфраструктуру и не вводит вторую
  систему авторизации.
- Результаты списков и dashboard описаны как реальные данные из PostgreSQL;
  fallback для недоступных интеграций не маскирует ошибки бизнес-метрик.
